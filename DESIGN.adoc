= Looprd: specification-driven companion server
:doctype: article

:revnumber: 0.1.0

== Agent diagnostics and failure history

Management can mint expiring, revocable, read-only capability URLs scoped to one
component or all components. Default lifetime is one hour, maximum twelve hours,
with at most 100 active links. Only token hashes persist in a separate versioned
local SQLite store. Capabilities never grant management or application access.
Machine-readable snapshots expose allowlisted health and structured failures,
with a public static OpenAPI reader contract. Raw status, repository addresses,
credentials, SQL, source code, application records and tracebacks are excluded.
Migration failures carry version/statement coordinates and safe database codes;
validation paths redact arbitrary names. Unknown errors remain generic. Failure
history is best effort, deduplicated, seven days/500 records, with at most 100
returned in scope. Historical failures remain distinct from current error state.
Existing status strings and specification/authentication contracts are unchanged.
Management UI retains Carbon styling and contained scrolling. Proxy operators
must redact capability paths in access logs. Backups preserve grants/revocations;
restoring an old backup can restore an old grant until its original expiry.
No new containers or component database migrations are required. See
docs/diagnostics.md for endpoint, retention and rollback contracts.

== Purpose

Looprd is one Python server hosting multiple small logical servers for ZipRunner projects.
Each project provides one self-contained specification containing its routes, models, authentication
policy, WebSocket subscriptions, optional inline handlers, and migration history.
The sources file connects these specifications to the runtime.
Adding a logical server requires no component container, process, listening port, or image build.
The shared runtime can run as one companion container on a Raspberry Pi.

== Implemented architecture

----
Local/HTTPS sources file -> watcher -> local/HTTPS/GitHub component specification
                                         |
                                  validated generation
                                         |
HTTPS entry point -> one ASGI dispatcher -> HTTP resources / inline handlers
                                         -> WebSocket resource events
                                         -> SQLAlchemy -> SQLite or PostgreSQL
----

Starlette handles ASGI, Pydantic validates specifications and CRUD input, and SQLAlchemy manages storage.
One ASGI worker owns the generation map and in-memory events/tickets. Do not run multiple workers.
SQLite files live in the persistent data volume. PostgreSQL is optionally an external/shared server;
SQLAlchemy is the data access layer, not a database server.
TLS and DNS belong to the existing reverse proxy/tunnel and host configuration.
The HTTPS hostname is configured in deployment and owned by the existing shared Traefik instance.
Public deployment examples use only `api.example.com`; private hostnames belong in operator-local copies.
`deploy/traefik/looprd.yml` adds only path-specific Looprd routing, preserves prefixes,
and reuses the existing TLS configuration. Backend addressing follows the host/container topology;
`docs/traefik.md` covers localhost, shared Podman networks, and separate hosts/engines.

Runtime dependencies are locked in `requirements.lock`. Component specifications do not install dependencies.
The package/CLI is `looprd`; the default component filename is `looprd.yaml`.
The specification contract is `looprd/v1`. Public prefixes are `/looprd/<component>/<version>`.
`/dapi` remains a compatibility URL alias, not a second specification format.

== Specification authority

=== Component frontend origins

Optional `cors.allowedOrigins` declares up to 128 unique exact frontend origins,
including custom WebView schemes with a host. Wildcards, opaque `null`, credentials,
paths, queries and fragments are rejected. The effective component list is the
union of this declaration and private `LOOPRD_ORIGINS` additions. If configured,
`LOOPRD_ORIGIN_RESTRICTIONS` intersects that union; an explicitly empty value
permits no browser origins. An omitted restriction leaves the union intact.
Legacy specifications keep their existing global-origin behavior. An explicit
empty component list adds nothing; it does not remove operator additions.

HTTP preflight and response headers use one captured active generation, for both
URL aliases. WebSocket handshakes use the same effective policy. Successful spec
reconciliation updates policy without a process restart; invalid candidates keep
the working policy and existing sockets follow the normal generation drain.
The policy is restored with the generation checkpoint. Component declarations
never grant cross-origin management access; management retains the global list.
Authentication and authorization remain required independently. CORS controls
browser response access, not client identity or server-side request authorization;
requests without an Origin keep existing native-client behavior. No cookies or
credentialed CORS are added. `cors.component` advertises this optional capability.
Effective lists are visible only in authenticated component management status;
private deployment additions are not copied into public OpenAPI or diagnostics.

`looprd/spec.py` is the executable contract. Generated JSON schemas are in `schemas/`.
`docs/specification.md` describes fields, operations, authentication, extensions, and migrations.
`examples/looprd.yaml` is a complete declarative component. `examples/python-handler.yaml`
shows custom logic embedded in the same file. No separate component source checkout is required.
Secrets are local references so specifications remain retrievable without embedding credentials.

== Sources and shutdown semantics

Branch/tag resolution requests GitHub's `application/vnd.github.sha` media type,
validates the returned 40-character commit hash, and fetches specification contents
at that immutable revision. It does not download commit diffs or file lists.
Pinned full commit hashes bypass lookup. Existing document-size bounds, token
containment and failed-fetch retention remain in force.

The sources location is configured through `LOOPRD_SOURCES` and may be a local file, HTTPS URL,
or `github://OWNER/REPO/path?ref=BRANCH_OR_COMMIT` location.
A valid sources document explicitly contains `apiVersion: looprd/v1` and `components: [...]`.
Each entry has a unique ID, specification location, and enabled flag. GitHub entries additionally
name a repository and ref. The reader resolves the ref to a commit and retrieves the spec at that commit.
Local paths resolve relative to the local sources file; remote relative paths resolve relative to its URL.
GitHub-relative specs resolve at the same immutable commit as the GitHub sources snapshot.
GitHub repository specs are retrieved through the authenticated Contents API using its raw media type.
`LOOPRD_GITHUB_TOKEN_FILE` supplies a mounted, read-only, fine-grained token and takes precedence
over `LOOPRD_GITHUB_TOKEN`. The file is reread for rotation. A missing configured file fails closed.
Credentials are sent only to GitHub HTTPS API/raw-content hosts on the default port; redirects are rejected.
One credential must cover the private index and all referenced private repositories under its resource owner.
`docs/private-sources.md` records setup and permission requirements.

Only a completely fetched and validated sources document is authoritative for removal.
An absent entry, `enabled: false`, or explicit empty components list stops new traffic to those servers.
The runtime drains existing work and closes WebSockets; it keeps databases and local secret files.
Successfully persisted removal is reflected in the startup checkpoint, so restart does not resurrect it.

An unreachable sources file, HTTP 404, timeout, invalid YAML, null/missing components list,
or any invalid source entry leaves the previous active set intact.
An unreachable or invalid individual component spec preserves that component's working generation.
Neither failure is treated as removal. Valid updates to other components can still proceed.
A new invalid component remains unavailable and is reported in management status.

== Generation reload

The watcher polls every 60 seconds by default. Reconciliation is serialized.
It compiles changed specs off the request path, validates secrets and database compatibility,
initializes candidate storage, and persists the next successful snapshot with atomic replacement.
Only then does it atomically replace dispatcher entries. Unchanged components keep their generation.
A failed candidate or checkpoint write preserves the existing dispatcher.

In-flight HTTP requests retain their original generation, bounded by the request deadline.
New requests use the new generation. Old WebSockets drain for 30 seconds by default and close with 1012.
After references drain, the old generation disposes its storage resources.
Components share an event bus across reload so old subscriptions can receive events while draining.
Events are bounded and best effort; clients must fetch current state after reconnecting.

Generation replacement does not use importlib.reload. Inline handler source is compiled into a new
namespace per generation. Inline Python is trusted code, disabled unless explicitly enabled on the host.
It must not have top-level external side effects or unmanaged background tasks.
Shared dependencies require companion image updates; no live pip installs occur.
Component token files are loaded on generation construction; restart or change the spec to rotate a token.
The management token is read per management request.

== Database lifecycle

SQLite column/composite uniqueness is verified against `PRAGMA index_list` and
`PRAGMA index_info`, including implicit indexes created by inline constraints.
DDL-text reflection alone may miss valid constraints on sized string columns.
Only full indexes of the declared columns qualify; partial/expression indexes
cannot substitute for whole-column uniqueness, and partial indexes do not match
declared full named indexes. PostgreSQL retains constraint/index reflection with
the same partial-index exclusion. This validation repair neither rewrites models
nor changes stored schema fingerprints; application migrations remain explicit.

Every component has separate SQLAlchemy metadata, engine, and session factory.
Every CRUD operation runs in its own transaction; independent tasks do not share sessions.
SQLite gets a persistent component-derived file with foreign keys and bounded lock waiting.
PostgreSQL requires an operator-provisioned dedicated database/role and connection secret.
A persistent identity record prevents accidental backend/connection-reference changes across reloads.

New databases create the latest declared schema. Existing model changes require an increased schemaVersion
and explicit inline migration statements. Migrations are ordered and recorded transactionally.
Automatic changes are limited to additive DDL; destructive SQL and downgrades are rejected.
Column names, type affinity, string lengths, nullability, primary keys, and required unique constraints
are checked before activation. The runtime never infers ALTER statements from model changes.

Migrations must remain compatible with old requests during draining. Failed SQLite migrations roll back
including DDL through explicit BEGIN IMMEDIATE; PostgreSQL uses transactional DDL.
A committed migration cannot be reversed by restoring a previous application generation.
A subsequent checkpoint failure can therefore leave the database ahead of the cached application spec;
restore matching data/state or repair deliberately before restart. Backups are an operator responsibility.
Removing a component never removes its database. Re-addition uses its retained identity and data.

== Authentication and management

Components explicitly choose public, shared bearer, or database API-key authentication.
Public/shared bearer modes retain component-wide access. Database mode requires a database,
an explicit scope vocabulary, permissions for every exposed resource operation and WebSocket resource,
and scopes on every custom handler. All listed scopes are required; incomplete or unknown policies
reject the specification. Generated OpenAPI carries scope requirements as vendor extensions.
There are no user accounts, passwords/login sessions, roles, row permissions, or implicit cross-component access.
Custom Python receives the authenticated principal for application-specific ownership checks.

Database mode adds a runtime-owned `_looprd_api_keys` table alongside application models in a transaction.
This table is outside the application schema fingerprint and version, so existing components can opt in
without changing their models. Application models/migrations must not touch runtime-owned tables.
Keys contain a random 256-bit secret and a lookup ID. Only a SHA-256 digest, granted scopes, label,
and creation/expiry/revocation timestamps are stored; the raw key is returned once on creation.
The existing admin token protects POST/GET `/_looprd/components/<id>/keys` and
DELETE `/_looprd/components/<id>/keys/<key-id>`. Creation validates declared scopes and defaults to
30-day expiry; explicit null permits non-expiring keys. These routes stay outside the public Traefik router.
No component client can provision its own keys. Key records are retained across reload/removal/restart,
and mode rollback retains the table. Re-enabling database mode restores retained keys and revocations.
Management list responses omit hashes and raw credentials. The GitHub source token remains separate.

HTTP authentication queries the component database on each request, failing closed on invalid,
expired, or revoked keys (401); insufficient operation scopes return 403 before executing handlers/CRUD.
In-flight requests authenticated before revocation may finish; there is no retroactive transaction rollback.
WebSocket subscriptions check resource scopes; outgoing events and one-second idle polling revalidate keys.
Revocation/expiry or a failed database check closes the connection with 1008. Database latency adds to
the polling interval. Event payloads include complete records, so event scopes grant access to those records.
WebSockets accept bearer headers or short-lived single-use browser tickets scoped to the generation
and authenticated identity. Database keys must permit a subscription to mint a ticket; redemption
revalidates the original key so outstanding tickets do not bypass expiry/revocation.
Browser origins must be explicitly allowed. HTTP CORS uses the same configured origin list.
Body sizes, pagination, request duration, and event queues are bounded.

`/_looprd/health` is public process liveness. `/_looprd/status` and POST `/_looprd/reconcile`
require the management key. On first startup without a mounted admin-token, Looprd generates
a random 256-bit key, prints it once to stdout, and retains only its SHA-256 hash in
`admin-key.json` under the persistent data directory. The file is owner-only; initial publication
is exclusive and atomic. Existing mounted admin-token files take precedence and are never printed
or overwritten. `LOOPRD_BOOTSTRAP_ADMIN=false` disables automatic provisioning; absent credentials
leave management disabled. Invalid persisted credentials fail startup instead of resetting access.
`python -m looprd admin-key --rotate` atomically replaces the generated hash and prints a replacement
to the command's terminal. Requests read the credential each time, so rotation invalidates the old
key without a restart. Mounted credentials must instead be rotated on the host.

`/_looprd/panel/` serves a public login shell for same-origin bearer-authenticated management calls.
The panel displays component status, reconciles sources, and creates/lists/revokes component keys.
It does not edit sources, deploy containers, or provision PostgreSQL. Credentials remain in page
memory unless Remember on this browser is selected (enabled by default at operator request).
That option saves the raw management key in same-origin localStorage and reconnects on reload.
Disconnect ends the live session while retaining the saved key; Forget key removes it and disconnects.
Unchecking Remember removes a previously saved key and uses session memory only. Rejected saved
credentials are removed. Storage failures preserve session access and are reported; failed removal
requires clearing site data. No cookies are used, and server responses never embed credentials.
Untrusted metadata renders
as text, with a nonce-based Content Security Policy, frame restrictions, and no-store responses.
Status additionally reports auth modes and declared scopes, never credential values.
The dashboard shows active, disabled and failed components, live request/socket counts,
route/model metadata, database backend, process-local load time, repository/ref and active revision.
It reports process uptime, source-check start/finish and last completed reconciliation,
draining generation count, browser origins and trusted Python policy. These are process-local
observations, not historical metrics or container resource/health probes. A completed reconciliation
can include failed components, reported separately. Source failures retain the last success timestamp
and last valid source summary. Specification URLs, credential references, handler source and response
bodies are excluded. Source summaries contain only validated repository URLs, refs and enabled flags.
The panel refreshes every ten seconds while connected and visible, with search/filter and an explicit
source check. Its HTML/CSS/JavaScript are bundled in the package as one nonce-protected page.
The panel uses official IBM Carbon v11 styles and the Gray 100 theme with native HTML/JavaScript.
Pinned npm dependencies and Sass build the stylesheet before Python packaging; generated CSS is
excluded from source control. Node is needed only for the UI build, not in the runtime image.
CI and a native-platform container build stage compile it; source developers follow ui/README.md.
Styles, including the Carbon license, ship locally with no CDN/font requests or additional framework.
The styling change has no persistence migration; an earlier image can restore the previous panel.
The default Traefik router excludes management; an optional management.yml.example explicitly
routes `/_looprd/` on the existing HTTPS hostname/service for panel use. Localhost/SSH access also works.

Normal logs expose component ID and error stage/type, never exception strings, SQL, tokens, or spec code.
First-start bootstrap and explicit key-generation commands are the deliberate credential-output exception;
container journals/logs containing that output must be treated as secrets. Restarts never reprint the key.
HTTP access logs are disabled to avoid logging ticket query strings.
Status reports active revisions, spec digests, schema versions, and failures.

== Operator API blocking

An authenticated PUT to `/_looprd/components/<id>/availability` with a strict
`{"blocked": true|false}` body sets a node-local override. Blocking gates both URL aliases,
all versions, documentation and ticket issuance with HTTP 503, rejects new WebSockets,
and closes existing connections with code 1008. Requests already executing may finish.
It retains loaded specifications, databases and keys; reconciliation can still update the
loaded generation. Blocking is distinct from removing or disabling a sources entry.
The override survives reload, restart and removal/re-addition and only explicit unblock clears it.
Unblocking never resurrects a removed/disabled component. Management stays available.
The versioned `availability.json` in the data volume is validated at startup and atomically
written before the override takes effect. Invalid stored state fails startup; write failure
preserves the previous override. Status exposes blocked IDs, including removed entries.

The Carbon panel has a fixed workspace with navigation between overview, components,
routes, models, access keys and runtime diagnostics. Long content scrolls inside contained
panels while the document remains fixed. Lists, model fields and diagnostic lines stay inside
the available viewport. Remembered credential lifecycle has dedicated Node tests in CI.
An explicit confirmation precedes blocking; production components are not blocked during deployment checks.

== Container delivery and Podman

The Containerfile runs as UID 10001, with data under `/var/lib/looprd` and config under `/etc/looprd`.
The GitHub image workflow runs Python tests, including an ephemeral PostgreSQL service,
builds and exercises a native container, then builds AMD64 and ARM64 images.
The Traefik smoke reads its request hostname from the deployed router's single literal Host matcher.
It rejects missing/ambiguous matchers instead of falling back to a hardcoded hostname.
Container smoke checks refresh the engine-reported published port after restart; ephemeral port
assignments are not assumed stable across a stop/start cycle.
Pull requests build without publishing; main/master pushes, version tags, and manual runs publish to GHCR.
Publishing starts only when this source is put in GitHub and its workflow runs.
The source repository is `https://github.com/pac-labs/dapi`; its image is `ghcr.io/pac-labs/dapi`.

Rootless Quadlet units in `deploy/quadlet` configure one runtime container and a retained named volume.
The config directory is mounted read-only so atomic host replacements remain visible.
The container root filesystem is read-only and host port 8080 binds only to localhost.
`docs/quadlet.md` gives installation, image update, reverse proxy, and backup instructions.
No automatic container update is configured; component specs still reload automatically.

== ZipRunner integration boundary

Looprd is intended as a ZipRunner companion, conceptually alongside RoboScope.
The supplied sources/spec files and authenticated status/reconciliation API form its integration boundary.
This change does not invent or modify parent project.zr fields or alter the ZipRunner application.
A future ZipRunner UI can register project specifications and display Looprd status through that API.
Keep the executable runtime contract and generated schemas here. A ziprunner-spec repository may
hold shared integration documentation and deployment/component sources without duplicating that contract.

== Validation and limitations

See `TESTING.md` for focused, full, PostgreSQL, and container smoke commands.
Acceptance includes multiple components in one process, independent reload, authoritative removal,
unreachable-source preservation, retained data, offline restart, and WebSocket reconnection.

Trusted Python extensions share the interpreter and can affect the whole runtime.
No hard per-component resource isolation, durable event replay, multi-worker coordination,
background job scheduler, database account provisioning, or destructive migration automation is provided.
Live Raspberry Pi/Quadlet behavior and ARM64 execution require deployment checks on Linux hardware.

== Temporary file transfers

The built-in Files workspace is independent of watched components and their schemas.
Only a management-authenticated operator can create/list/delete invitations and files.
An invitation contains a validated display filename and a random 256-bit single-use upload
capability. The raw capability is returned once; only its SHA-256 hash is persisted.
PUT of raw file bytes consumes the invitation, with no management key required by the sender.
It accepts one stream, never a multipart collection. Failed/interrupted accepted uploads consume
the invitation and discard partial bytes; quota rejection before claiming permits a later retry.
A separate random 256-bit download identifier is disclosed to the uploader and panel only after
completion. There is no anonymous listing or filename-based lookup. Downloads need no login,
are attachments with application/octet-stream, no-store, nosniff, and sandbox headers.
Deletion is authenticated and uses DELETE, never a side effect of visiting a URL.

Files and invitations expire 12 hours after invitation creation (uploads do not extend this).
Expired links are immediately denied on lookup. A 30-second sweeper removes expired bytes and
metadata while the runtime is running; startup removes expired and interrupted upload data.
Physical storage on a stopped host cannot be swept until restart. Persistent bytes and SQLAlchemy
SQLite metadata live below the existing data volume at files/, independently of component databases.
This operational store requires no PostgreSQL application role or component migration. Its v1 table
is named files_v1; rollback to an older image leaves the directory untouched until a compatible image
is restarted. Backups may retain copies independently of live retention and must be handled by operators.

The one-worker runtime serializes claims/metadata changes. Uploads stream to disk outside the event
loop, enforce a five-minute upload deadline, reserve their maximum size against total quota, and
publish download readiness only after successful close and metadata commit. Restart never publishes
partial files. Default limits are 100 MiB per file, 1 GiB reserved/ready bytes, and 128 live records.
LOOPRD_FILE_MAX_BYTES and LOOPRD_FILE_QUOTA_BYTES configure host limits, without extending retention.
Upload URLs are not placed in localStorage, diagnostics, or Looprd access logs. Operators must omit
these capability paths from reverse-proxy access logs as they do WebSocket tickets.
The panel constructs absolute commands/links from its current origin; JSON API URLs are same-origin
relative paths, avoiding trust in forwarded hostname/scheme headers. Public Traefik examples include
only upload/download prefixes, keeping listing and management private unless explicitly enabled.

== Optional Redis event fanout

The reviewed proposal and compatibility decisions are recorded in docs/redis-review.md.
A component may add realtime with backend memory (default) or redis, delivery best-effort,
and connectionSecret required only for Redis. Existing v1 descriptors and WebSocket JSON
remain valid and unchanged. Unknown durability/auth/topic options continue to be rejected.
Older strict runtimes reject new fields; upgrade the runtime before opt-in and remove new
fields/checkpoint entries deliberately before a runtime downgrade. No database migration
or looprd/v2 is needed for this optional transport.

An event hub keeps the existing local bus per component. Generation-bound facades retain
synchronous publish/subscribe behavior, deliver locally immediately, and enqueue a bounded
best-effort remote send. Transport connections are reference-counted across candidates and
draining generations, closed on failed construction/checkpoint, retirement/removal and shutdown.
Redis connection errors never change committed CRUD success or local notification delivery.
Missing/invalid local secrets reject configuration; server outages reconnect with bounded backoff
and expose sanitized connection state/drop counters through protected management diagnostics.

Exact Redis channels include LOOPRD_EVENT_NAMESPACE (default looprd), component and API version.
Deployments sharing Redis must use distinct namespaces unless cross-runtime delivery is intended.
Database numbers do not isolate Pub/Sub. Envelopes carry version, random event ID and runtime
origin; own-origin messages and bounded recently seen duplicates are suppressed. Payloads and
outgoing queues are bounded. Redis does not authorize clients: all existing resource scopes,
revocation checks, origin validation, tickets and component blocks remain enforced by Looprd.
Clients must recover from lost notifications by fetching authoritative SQL/application state.
There is no outbox, durable replay, presence, user identity, private-topic authorization, or
multi-worker guarantee in this change. Redis peers in one namespace are trusted equivalent
runtimes; connect only deployments serving the same authorized resource contract/data.

Optional companion Quadlets create an isolated Redis network and memory-bounded server with
an operator-mounted ACL file, no published ports and no persistent application data. An optional
Looprd drop-in attaches to that network and orders Redis startup. Existing installations retain
their current containers/networks unless explicitly opting in. Durable business data stays in SQL.

== Generic platform passes

The accepted four-pass sequence and compatibility boundaries are recorded in
 docs/platform-passes.md. Looprd provides storage, authenticated access, authorization,
transactions, events and reusable infrastructure; application behavior remains in components.
Authentication extensions must be optional and provider-independent. Public, bearer and
database modes remain supported. Applications own accounts, credentials, recovery and device
sessions. Additional verifiers establish a generic principal only through trusted server-side
verification, never by accepting a client-supplied user ID. No OIDC provider is required;
OIDC is a possible future adapter, not a prerequisite or an implemented capability.

Pass 1 adds opt-in SQL-backed durable events and capability requirements. Atomic event writes
are guaranteed for native CRUD and the supplied transaction-bound emitter, not arbitrary trusted
code using its own transactions or legacy publish. Commit ordering is serialized through a SQL
clock row; sequences/cursors remain stable across restart. SQL replay and polling recover from
lost best-effort Redis notifications. Retention gaps are explicit, history/capacity and response
pages are bounded, and replay uses the same resource authorization as WebSocket subscriptions.
Default descriptors, event payloads and in-memory behavior stay unchanged. Runtime-owned event
tables are versioned separately and retained when durability is disabled or a component removed.
Unsupported required capabilities reject candidates before activation and preserve working ones.


Pass 2 uses trusted optional Python verifiers and an identity contract scoped by explicit realm.
Owner/membership policies guard native CRUD and event/replay delivery; custom SQL remains trusted
application code responsible for domain checks. Current memberships and session validity are
rechecked during subscription delivery. Application account/session ownership stays outside core.

Pass 3 adds declared structural constraints, bounded scalar filters/keyset cursors, read-only
projections and compare-and-swap revisions. Explicit additive migrations remain mandatory for
model changes; unchanged legacy fingerprints stay stable. Local service calls use declared,
versioned JSON contracts and caller-bound machine credentials through normal HTTP authorization.
They provide neither user impersonation nor cross-component/distributed transactions.

Pass 4 adds optional bounded memory/Redis rate counters, local in-flight/socket caps and serialized
native SQL row quotas. SQL jobs have persistent schedules, bounded queues, leases, at-least-once
retry and stale-completion checks. Applications own job idempotency. Runtime directory ownership
is OS-locked; schema initialization is SQL-locked and component-owned. These protections do not
remove the one-worker constraint for tickets, uploads, checkpoints and operator blocks.
Optional bounded process execution is a fault-control boundary for trusted pure-JSON handlers,
not a security sandbox. Inline execution remains cooperative and trusted. Historical local
metrics/audit are bounded best-effort metadata, omit payloads and credentials, and are exposed
only through authenticated management. Operational guarantees and rollback limits are specified
in docs/platform-reference.md; production components opt in independently.


== Host container metrics

An optional host-owned sampler observes only the fixed Looprd/PostgreSQL/Redis
container allowlist through read-only Podman CLI calls. It atomically writes a
sanitized snapshot into the existing read-only configuration-directory mount.
The runtime has no container-control socket, host command execution or write access.
Authenticated Operations reads bounded, validated snapshots with explicit stale,
disabled and unavailable states. CPU uses sampled deltas; unsupported memory remains
unknown. Environment, credentials, addresses and unrelated container data are excluded.
The sampler is a systemd timer, not an additional container or telemetry service.
Existing services/networks and kernel configuration remain unchanged. Optional public
PostgreSQL Quadlets fill the deployment template gap without replacing existing units.
