= Multiplayer integration examples
:revnumber: 1.0.0
:revdate: 2026-10-19

These are integration fragments for existing Looprd 0.2.0 facilities, not a new
platform contract or complete replacement components. All origins and IDs are
synthetic. No file here contains an actual secret, creates an account or authorizes
a migration/deployment. See docs/MULTIPLAYER_PREREQUISITES_REVIEW_1.0.adoc.

== Atrium connection

The operator registers atrium-deployment.json through the actual Atrium
`POST /looprd/atrium/v1/registry/discovery/v2/manage` route with an Atrium
apps:approve application credential. This is NOT a Looprd management credential.
Provision a separate Atrium component key with scope apps:discover only and
service subject matching callerSubject. Provisioning is an operator action, not
something a game or browser performs. Do not read keys back from logs.

Keep that key in the sender's mounted secrets under the reference in
sender.env.example. The sender checks capabilities before delivering. Hostname
approval is configuration; this example does not prove any endpoint is live.
For another Looprd instance use a distinct deploymentId, callerSubject, public
origin and credential. Neither sidecar needs changing.

`launchOrigins` may remain empty. Missing hosting configuration leaves browser
launch unavailable while metadata registration still succeeds. API availability,
game launch and a player's permission to join are separate concerns.

== Life and Social on one Looprd instance

life.dependencies.yaml is a FRAGMENT, not a valid whole component. Merge it into
Life's existing looprd.yaml only with Life's server-side adapter. The referenced
Social service key is a separate credential from the Atrium discovery key.

Social's actual verified adapter uses the existing host variables:

[source,text]
----
LOOPRD_SOCIAL_SERVICE_SECRETS_JSON={"the-life-loop":"tavi/services/life"}
LOOPRD_TAVI_GAME_CALLERS_JSON={"the-life-loop":["life.loop"]}
LOOPRD_TAVI_SOCIAL_ISSUER=example-social-installation
----

The mapping contains a secret reference, never its value. The issuer must be the
stable identity of this actual Social installation. Retain any other configured
callers/issuers rather than replacing host settings with this example.

Inside Life's trusted server handler, use the existing calls:

[source,python]
----
identity = await ctx.call('looprd-social', 'tavi-game-grant-redeem', {
    'grant': user_supplied_single_use_proof,
    'gameId': 'life.loop',
    'matchId': match_id,
})
# Life must check accepted, issuer, subject, game/match and its own seat policy.
# An error or accepted=False must never fall back to trusting a client user ID.
----

This is a call illustration, not an implemented Life handler. The short-lived
proof belongs in an HTTPS body; a Social login session or machine key must not
be placed in the launch URL. No game rules or invitations belong in Looprd core.

event.json matches Social's existing tavi-game-event/v1 request schema. Deliver it
from a server-side Life outbox after the game transaction; keep the same eventId
on retry. A repeated request is application-idempotent in Social. ctx.call does
not itself make a cross-component transaction or persist an arbitrary retry queue.
Use tavi-game-room-roster/v1 only if Life implements verified full-seat snapshots.

When Social runs on another Looprd server, these ctx.call examples do not route
there. Use reviewed HTTPS server-to-server transport and the target's normal
service credential, authorization and idempotency policy. Never expose that
machine credential to the Tavi browser/native frontend or an OpenClaw chat.

== Reproduce source-only interoperability checks

Obtain the exact reviewed source revisions listed in the review. Place complete
Atrium descriptors/includes under `<sources>/atrium/` and Social's descriptor
under `<sources>/social/`. Source handlers are trusted code; review before execution.
No test downloads source or creates an external account.

[source,powershell]
----
$env:LOOPRD_INTEGRATION_SOURCES = '<absolute-reviewed-sources-directory>'
python -m pytest -q tests/test_multiplayer_interoperability.py
python -m pytest -q
npm run test:ui
npm run test:clients
----

Without LOOPRD_INTEGRATION_SOURCES the two external interoperability tests skip
explicitly. The existing synthetic service/discovery tests still run normally.
