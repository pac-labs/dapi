== Conclusion and scope

Governing authority: DESIGN.adoc / Specification authority (Automatic Atrium
discovery delivery and generic platform extensions), Authentication and management,
Generation reload and Database lifecycle. The existing DESIGN fingerprint in
PROJECT_PLAN.adoc remains unchanged; this review does not amend platform contracts.

The existing generic Looprd 0.2.0 contracts are sufficient for the requested
same-runtime Life / Social service integration and authenticated Atrium discovery.
No runtime patch or protocol redesign is justified by this review. This pass adds
interoperability tests and configuration examples, not game behavior or deployment.
The running discovery connection is NOT configured or enabled.

The previously reported Atrium v1/v2 mismatch is superseded by the actual receiver
in current Atrium source. A real DAPI transport-to-receiver test now passes; it
does not prove production credentials, the production receiver configuration,
Internet delivery, browser/OpenClaw play or application authorization end to end.

== Application implementation gaps are not platform gaps

Life's schema 3 contains persistent GameMatch / GameParticipant / GameInvitation /
GameAction / GameCheckpoint / GameNotificationOutbox storage. The presence of those
models and internal async code does not expose an authenticated play API: the actual
looprd.yaml has no /play handler or declared Social dependency. Metadata advertising
a multiplayer role does not prove persistent human-vs-OpenClaw gameplay works.

Life must connect its own handlers to its own match logic and the existing Social
contracts, verify identities and seat/turn permissions, and retry domain events
after committing game state. Native ctx.emit can join its local SQL transaction;
cross-component calls cannot. Legacy ctx.publish after commit is best effort.
Use existing jobs/event replay/outbox primitives as appropriate; do not add game
invitations, deadlines, turn evaluation or approval logic to Looprd.

Social's configured service secret mapping establishes machine identity, not a
user identity. Its issuer, game-caller policy and subscription checks are application
configuration. No external identity provider is required. Neither trusted discovery
nor a service key makes a client-supplied user ID trustworthy.

Atrium's v2 metadata catalog is separate from its immutable public release catalog.
Automatic metadata registration does not create a browser launch, player grant,
asset approval or game seat. Those remain Atrium/Life/Social application features.

== Minimal integration examples

See examples/multiplayer-prerequisites-v1/README.adoc and adjacent declarative files.
They contain placeholder origins, secret REFERENCES and synthetic account/event
identities only. They are not full application replacements or runnable installers.
The Life dependency fragment is specifically NOT installed in the reviewed Life
descriptor. Provision the credential outside source and merge the fragment only
when Life implements the corresponding calls. A call failure must not authorize play.

== Verification and limits

tests/test_multiplayer_interoperability.py uses explicitly selected, pinned upstream
descriptors, generated Atrium handlers and Social verifier under the real DAPI ASGI
runtime. It creates disposable SQLite databases and random machine keys. It does
not fake a receiver acknowledgement or use production secrets, accounts or addresses.
Both logical deployment identities share one local test receiver; no separate host,
TLS termination, reverse proxy or Internet network has been exercised by that test.

The test covers all three provenance kinds, wrong key/deployment, automatic reviewed
registration, duplicate/reordered messages, lost reply after commit, sender/receiver
restart, update and withdrawal with another deployment still available. Social proof
redemption is intentionally a nonexistent grant: valid service authentication and
fail-closed domain behavior are verified, not a successful player invitation flow.
Existing discovery tests cover source changes, invalid/unavailable metadata,
configuration failure isolation, confirmed removal and retained pending delivery.

The new interoperability tests are opt-in when upstream source is supplied; they
must visibly skip rather than silently fetch mutable repositories during normal CI.
See the adjacent examples README for exact commands. Producer logs are recorded in
evidence/multiplayer-prerequisites-1.0/. PostgreSQL/Redis integrations and real
multiplayer/operator acceptance must be reported separately, not inferred from SQLite.

== Follow-up ownership; no Workboard completion claims

* DAPI-CONFIG-DISCOVERY: operator provisions the scoped receiver connection and
  enables only after staging acceptance; this pass performs no configuration change.
* LIFE-SOCIAL-ADAPTER: Life exposes its own game API and consumes the declared Social
  proof/event contracts, with local authorization, transactions and durable retries.
* MULTIPLAYER-E2E: application owners verify real accounts, invitation redemption,
  persisted seats, turns, reconnect and OpenClaw play through the actual clients.
* CROSS-HOST-TRANSPORT: needed only if those application calls span Looprd instances;
  review actual topology before proposing a generic remote transport extension.

These are follow-up descriptions, not mutations of trusted operator Workboards.
Existing source receipts, project identity and manager/operator decisions are kept.
No migration, credential rotation, runtime-state edit, push or deployment is authorized
or performed. No versioned runtime patch is necessary; the runtime remains 0.2.0.
